================================================================================================
Milestone 4 open question 4 (task 25): does an unroll factor above 1 pay?
================================================================================================

Two chain depths (8, the named short candidate; 20, the dayofweek-shaped long candidate) times
three outer-loop unroll factors (K = 1, 2, 4), each over one N=4096 row buffer (one Spark
COLUMN_BATCH_SIZE). Every K variant is fully straight-line unrolled source (no runtime loop over
the op index) so K=1 and K>1 differ only in how many independent lane groups are interleaved per
outer-loop body, not in loop-control shape. See VarkaUnrollFactorBenchmark.java. Run four times
total: twice before PR #56 (task 24) merged and twice after, with the machine's performance mode
enabled for the second pair. All four runs agree in direction and rough magnitude on every case;
neither the merge nor performance mode changed a conclusion.

OpenJDK 64-Bit Server VM 25.0.4+7-1-26.04-Ubuntu on Linux 7.0.0-30-generic
AMD Ryzen AI 9 HX PRO 370 w/ Radeon 890M, machine otherwise idle
JMH 1.37, throughput mode, forks=0 (in-process, on the surefire JVM), 1 thread,
3 x 2 s warmup, 5 x 2 s measurement. Higher is better.
Run: ./build/mvn -f sql/varka/engine/pom.xml test -Dvarka.jmh=true

--- Reading these numbers (ratios by minimum-of-5, across all four runs) ---

* Depth 8 (short chain): flat across K = 1, 2, 4 at both widths, on every run - within 4% either
  way, no consistent direction. The honest null hypothesis in PLAN_MILESTONE_4.md section 2.3
  holds here: C2 plus the out-of-order engine already collect the available overlap on a body
  this short, so unrolling buys nothing (and is not measured to cost anything either, at least at
  K=2 or K=4 on this shape).
* Depth 20 (dayofweek-shaped long chain): unrolling by K=2 wins reproducibly at both widths and
  on every run - +2.6% to +9.2% at AVX-512, +1.2% to +6.2% at 128-bit. K=4 adds no further,
  consistent benefit over K=2 on either width (the sign varies run to run, always within a few
  percent) - the benefit saturates at K=2, which is also the cheaper choice against GROUP_BUDGET.
* Net for task 25: "K pays only on the long chains" is confirmed, not just predicted, and the
  planner version the task's design calls for should have a ceiling - K=2 for a chain this long,
  not an unbounded search - since K=4 was measured to add nothing further on the one shape where
  unrolling helped at all.
* Methodology note: an earlier version of this benchmark measured K=2/K=4 through a small
  constant-bound runtime for-loop over the op index, rather than the fully unrolled straight-line
  source above. That version showed K=4 losing 30-60% at some shapes - an artifact of comparing a
  loop-shaped baseline against a straight-line K=1, not a real unrolling cost. Discarded before
  being trusted; see the `SKILLS.md` entry this measurement added.
