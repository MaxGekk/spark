================================================================================================
Milestone 4 pre-registration measurements (JMH)
================================================================================================

Five candidate-lowering comparisons for tasks 27, 28 and 30 (not yet started), each over one
N=4096 row buffer (one Spark COLUMN_BATCH_SIZE, L1/L2-resident). See
VarkaMilestone4MeasurementsBenchmark.java for what each pair measures and why. Run four times
total: twice before PR #56 (task 24) merged and twice after, with the machine's performance mode
enabled for the second pair. The "Reading these numbers" section cites the full spread across all
four runs; nothing in PR #56 touches code this benchmark exercises, and performance mode did not
change any conclusion - only some margins, both directions, by a few points.

OpenJDK 64-Bit Server VM 25.0.4+7-1-26.04-Ubuntu on Linux 7.0.0-30-generic
AMD Ryzen AI 9 HX PRO 370 w/ Radeon 890M, machine otherwise idle
JMH 1.37, throughput mode, forks=0 (in-process, on the surefire JVM), 1 thread,
3 x 2 s warmup, 5 x 2 s measurement. Higher is better.
Run: ./build/mvn -f sql/varka/engine/pom.xml test -Dvarka.jmh=true

--- Reading these numbers (ratios by minimum-of-5, across all four runs) ---

* Alignment: aligned beats misaligned at both widths, on all four runs - 1.56x to 1.79x by min at
  AVX-512, 1.22x to 1.25x at 128-bit. Real, reproducible, and scales with width: bigger where a
  load spans more of a cache line. Unaffected by the merge or performance mode.
* Boolean materialization (a single comparison): toVector+and and blend are statistically tied at
  both widths across all four runs - which one leads flips between runs, by up to 1.11x either
  way, always within this file's own noise band. Whether to skip materializing an int column at
  all is the real, width-dependent finding, reproduced on every run: not materializing (bits-only
  straight to the packed bitmap) wins by 1.10-1.18x at AVX-512 but *loses* by 1.40-1.60x at
  128-bit - the strategy should not be picked once and assumed to generalize across widths.
* Lane-width conversion: narrowest-drive and part-loop are tied at both widths on every run
  (within 1.01x-1.07x either way) - narrowest-drive is the simpler build (one trip count) for the
  same throughput.
* Boolean trees ((a > b) AND (c < d)): tied at AVX-512 - the winner flips between runs, by up to
  1.07x either way - but mask-space wins reproducibly at 128-bit on every run, 1.24x-1.37x - never
  worse, sometimes decisively better.
* Division safety: blend-then-div beats masked-div at both widths on all four runs - 1.08x-1.10x
  at AVX-512, 1.18x-1.19x at 128-bit by min. The one measurement whose margin stayed under 1.3x on
  every run; still consistent in direction and magnitude across all eight data points (two widths
  times four runs), which is the interleaved-comparison the under-1.3x rule asks for.
