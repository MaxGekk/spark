== shapes and arms ==
The IR is built by hand and emitted through VarkaLoopEmitter.emit with the option set of the arm; the kernel is
loaded with VarkaGeneratedClassLoader and called with the same arrays the evaluator passes, a byte column one byte
a row and an int column four. All four shapes are TINYINT:
  a  y1 < y2, a selection: two byte columns, one compare, the output the packed selection bitmap.
  b  (y1 + y2) < y1, a selection: three nodes (two leaves, a WRAP add, a compare). The columns hold bytes in
     [-64, 63], so no byte sum overflows and the arms and the reference can agree before row 330's deferred wrap
     (the overflow probe below shows what happens where they cannot).
  c  b < i, mixed and int-driven: a byte column widened to INT against an INT column. The tree holds an int value,
     so both arms emit the int lane; the run checks that the two arms' class bytes are identical (they are).
  d  the packed boolean output of a byte compare: the same kernel as (a). A boolean output in the IR is a condition
     root, whose only write is the selection bitmap, so the fourth shape and the first are one emitted kernel
     (VARKA-329.md 9.2 said as much); there is no separate kernel to emit or time.
  e  CASE WHEN y1 < y2 THEN y1 ELSE y2 END, a TINYINT store: the store shape the spike lacked, a narrow value
     written one byte a row.
WIDENED (the default, narrowLanes=false) computes in the int species: a byte column is loaded as the byte species
of the int species' width - 16 lanes (128 bits) at 512, 8 lanes (64 bits) at 256, and none at 128, where the 4-lane
byte species would be 32 bits and does not exist - B2I to the int species, int compare and arithmetic, and a store
narrowed once at the write. NATIVE (narrowLanes=true) computes in the byte species where every value is narrow:
64 lanes at 512 (one whole selection word a group), 32 at 256 (half a word), 16 at 128. The byte lane count is 0 at
512 and 256 because no width-specialised validity pair exists for 64 or 32 lanes, so those arms run the general
validity path; at 128 bits the 16-lane pair is specialised.

== harness and checks ==
Row 407's rule, driven by VarkaEmitterTestSupport.awaitC2Idle/loopLevels/allLoopsC2: each arm at its own turn, just
before it is timed, for at least 8 drives and then until two consecutive drives are within 30 percent, with C2 idle
after each drive and every dense loop method of the kernel at level 4. All 210 case settles over the 10 runs below
took exactly 8 drives, none printed "did not settle", and every one read level 4.
Every arm's whole batch is compared with VarkaReference before it is timed (the interpreter) and again after the
code is compiled; 420 comparisons, all agreeing. A selection root is compared a row at a time against the
reference's truth, a store root against the reference's value and validity, with the empty output validity read as
no nulls.
Timed: Spark's Benchmark, at least 3 iterations after a 1 s warm-up, 1 s minimum; an iteration is 2^27 rows
(repeats of the same column pair), so Best Time is 134.2 M rows and the Rate column is the figure used. Rows are
multiples of 64, so no loop has a tail. The timing path allocates nothing (the call arrays are made once a case).

== refusals at 128 bits (printed by the run, not inferred) ==
  a, WIDENED: a BYTE column has no widening load at 4 int lanes
  b, WIDENED: a BYTE column has no widening load at 4 int lanes
  c, WIDENED: a BYTE column has no widening load at 4 int lanes
  e, WIDENED: a BYTE column has no widening load at 4 int lanes
  c, NATIVE: a BYTE column has no widening load at 4 int lanes
Shape c refuses under NATIVE too because it is int-driven: the byte column is widened at a load whatever the arm,
and at 4 int lanes the byte species would be 32 bits, which the Vector API does not have. So on a 128-bit host
(the Neoverse N2 CI runner) the default arm has no emission at all for any TINYINT kernel that reads a value, and
the row engine answers; NATIVE serves the all-narrow shapes only. The census's two 128-bit byte-load forms
(B2I_load64 and B2I_load128, 9.2) load a 64- or 128-bit byte species and convert in parts, which is more than one
int group an iteration; the emitter computes one group an iteration by design, so it cannot use either. 2.3's
question is answered for the intrinsics and not for this emitter.

== predictions of 3.3, scored on the emitted arms ==
1. Byte compare in L1 and L2, NATIVE over WIDENED between 1.5 and 4.0: holds at 256 bits (3.02 at 16384 rows);
   at 512 it reads 4.05, at the ceiling and just above it as the spike's hand loops were (5.60). The bound that
   failed for the hand loop is met by the emitted kernel at 256 bits and touched at 512.
2. Past the last-level cache, the ratio within 0.85 to 1.3: the 8388608-row rung is not past L3 for bytes (a
   16 MB byte pair against the pinned complex's 16 MB), and there the ratio is 1.58, above the band; at 33554432
   rows (a 64 MB pair, past the cache) it is 1.17 for the compare and 1.24 for the chain, inside the band. So the
   prediction holds at the rung that is genuinely past the cache; the 8388608-row rung is at its edge, the
   correction 9.2 already made.
3. Mixed int-driven `b < i` within 0.85 to 1.3 at every rung and width: 1.00 at every 512- and 256-bit rung, and
   the two arms' class bytes are identical; at 128 bits both arms decline by name.
4. SMALLINT: not measured here, the four shapes of this step are TINYINT. The spike's numbers stand.
5. At 128 bits, the ceiling of 4.0 for bytes: there is no emitted ratio to bound, because WIDENED declines and
   NATIVE declines the int-driven shape. What the emitted arm reads at 128 bits is 34 to 36 G rows/s for the
   compare, 83 to 90 percent of the hand loop's NATIVE rate.
6. The two-species case: holds at 512 and 256 - no refusal, both arms in one JVM, and the separate-arm JVMs within
   1 percent of the all-arms ones. At 128 bits the census cells decide, and one of them (the widening load at 4 int
   lanes) does not exist, which is the refusal above.
7. The tiering artefact: holds - 210 settles, all at 8 drives and level 4, none unsettled, and no cell moved with
   run order. The largest run-to-run spread is 14 percent (a, 262144 rows, NATIVE, 87.5 to 99.7 G rows/s over the
   five 512-bit runs), which is why the tables are medians.

== the arithmetic overflow probe (what shape b does not measure) ==
Sixty-four rows of 100 and 100, emitted shape b, both arms, one run each:
  WIDENED: status 0, the first four selection bits 0000 (an int add says 200 < 100 is false)
  NATIVE:  status 0, the first four selection bits 1111 (the byte add wraps to -56, and -56 < 100 is true)
VarkaReference adds in ints, so it sides with WIDENED; Spark's own answer is the wrapped one. That is row 330's
deferred wrap (VARKA-329.md 4.2), which is why shape b's timed rungs use bytes in [-64, 63] and the probe is not a
result: it is the demonstration that the two arms cannot be compared on overflow data until 330 lands.
