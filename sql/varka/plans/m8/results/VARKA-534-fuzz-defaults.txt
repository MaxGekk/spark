## 1. Where the finding comes from

The option matrix's suite profile (fix 3; sql/varka/plans/m8/results/VARKA-suite-profile.txt on
branch varka-suite-profile, row 532's, not yet on master), laptop numbers of 29 October 2026:
under cse=false VarkaSmallTreeSuite's reach filter (VarkaReach.ranAtDefaults) emits every tree
under the configuration and again under the defaults and runs it only where the bytes differ:
141869 trees emitted the same bytes and 7902 moved, and half of the 44.1 s of emission and IR
sampled was the defaults' copy, which every configuration's JVM emits again.

What the code on master does, read before building:
  VarkaSmallTreeSuite         emits each filtered tree under the configuration, then again under
                              the defaults to the same class name, and compares the bytes.
  VarkaIrFuzzSuite            its one reach site, the compiled test, compares options alone
                              (bytes and emitter null); the random draws (runOne, runOneLong,
                              runOneMixed) are not filtered. It emits nothing at the defaults
                              for the filter, so there is nothing for a store to replace.
  VarkaCoverageCompositionFuzzSuite
                              compiles each case at the defaults (compilePartial) and emits each
                              kernel there again (reachBytes) - the same double work in a third
                              suite, not built here (section 6).

## 2. What was built

VarkaFuzzDefaultsStore (sql/catalyst test sources), named by -Dvarka.fuzz.defaultsStore=<dir>:
  a JVM of the defaults (varka.matrix.config unset) keeps, for each tree VarkaSmallTreeSuite
  filters, the SHA-256 of the class it emitted to at VarkaEmitOptions.DEFAULTS, or a mark that
  the emitter declined it, and writes fuzz-defaults-<pid>-<nanos>.bin into dir as it exits
  (gzip, written to a .tmp and moved, as row 528's harness store does). It never reads.
  A JVM under a configuration reads every fuzz-defaults-*.bin there as it starts. For a tree it
  finds, VarkaReach compares the SHA-256 of the JVM's own bytes with the stored one; a tree the
  store lacks is emitted at the defaults as before.
  The hash is of the whole class file, constant pool included: a per-method hash of the Code
  bytes would miss two classes whose methods name different constants by the same pool index.
  The key is SHA-256 of the suite, the class name, the inputs, the literals, the canonical roots
  and the host: the UseAVX level, the preferred vector lengths per element size and the JDK
  version, which the emitter and the class-file library read from the JVM.
  The header holds the commit (the revision in spark-version-info.properties, the build's) and a
  hash of the options table (each option's kind, name, reason and default text, the choices'
  constants, and the defaults' canonical text). A file of another commit or table, a file that
  cannot be read whole and a tree two files disagree on are ignored, with a VARKA_FUZZ_STORE
  warning line on stderr; a JVM that cannot read a 40-hex commit neither writes nor reads.
  Each JVM prints one line as it exits:
    VARKA_FUZZ_STORE  WRITE|READ  <config>  entries N  taken N  emitted at the defaults N
        files ignored N

VarkaSmallTreeSuite names each kernel by the test, the lane and the tree's index
(VarkaSmallTree[Long][Pair]<index>) instead of a per-JVM counter, so a tree is the same class in
every JVM whatever tests a reach file skips before it. Under a configuration it prints, beside the
VARKA_REACH line, a VARKA_REACH_SET line: the count of trees skipped and of trees run, each with
an order-free digest (the sum of each tree's key hash's first 8 bytes), so two runs print the
same line exactly when they skipped and ran the same trees.

VarkaFuzzDefaultsStoreSuite (JUnit, 0.8 s): over the int and long series to size 2 and three
configurations (cse=false, misdescribeAdd=true, validityByBitmap=false), the store's verdict
equals the second emission's tree by tree, with no tree emitted again and the tallies equal; a
tree the store lacks is emitted at the defaults; a file of another commit and one of another
options table are ignored with a warning and the filter emits again; a missing directory reads
as empty; a truncated and a garbage file are ignored whole beside a good one that is read whole;
a tree two files disagree on is left out; a writing store answers nothing and keeps only
emissions under the defaults' options; a tree the defaults declined moves.

The second run without the store met another agent's load (the 1-minute load rose from 4.86 to
13.73) and is not read. Of the three undisturbed runs, writing cost 131.5 and 132.7 s against
126.7 s without: some 5 s, inside what one pair can tell; the keys (the canonical text of 149771
trees) and the hashes are the work, and the file is written at exit. Two writing JVMs wrote the
same entries: the two files, decompressed, are byte for byte equal, so the defaults' emission of
every tree is the same in two JVMs, as the store assumes.

The store: 149771 trees (113721 int, 32891 long, 3159 pairs: the trees the defaults checked, 0
declined), one file of 9714900 bytes gzipped (32-byte key and 32-byte hash a tree, which gzip
cannot shrink). The defaults' counts are the profile's: 113721, 32891 and 3159 shapes checked.

## 6. Not built, and the CI wiring

The CI wiring, described and not added (this change edits no workflow and not
dev/varka_matrix_bins.py):
  (a) A defaults JVM of VarkaSmallTreeSuite at the matrix's size, 4, runs with
      -Dvarka.fuzz.defaultsStore=target/varka-fuzz-store and uploads the directory as an
      artifact, varka-fuzz-defaults-store; the option matrix's bins download it from the same
      run that gave them the test classes (dev/varka_matrix_reuse.py's run) and pass
      --jvm-arg -Dvarka.fuzz.defaultsStore=<dir> on the SmallTree units.
  (b) Where it is written matters. The Build's catalyst Varka jobs run the series at size 3, the
      pull request's size; a store of theirs holds the trees to size 3 only, a few thousand of
      the 149771 at size 4, so the bins would emit most trees at the defaults again. Either a
      catalyst job runs the two series tests at size 4 at the defaults with the store (the cost
      of section 3, some two minutes on the laptop, more on a 4-core runner), or the matrix
      writes it in its own defaults unit of SmallTree and runs SmallTree's configuration units
      after that unit, which puts a dependency inside the bins' plan.
  (c) The commit: the header's commit is the revision in the build's
      spark-version-info.properties, which travels in the classpath archive the bins unpack, so
      a store written by the Build whose classes the matrix reuses always matches, and one from
      any other build does not and is ignored with a warning.
  (d) The host: the runner pool mixes 256-bit and 512-bit machines (VARKA-399), and the vector
      lengths are in the key, so a bin on the other kind finds no tree and emits them all at the
      defaults, as today. One store per kind (two writers) would serve both.

Outside this row's scope, found on the way:
  VarkaCoverageCompositionFuzzSuite emits and compiles each case at the defaults again for its
  filter (section 1); the same store would serve it, keyed by its case.
  VarkaIrFuzzSuite's random draws are not reach-filtered at all; whether to filter them by bytes,
  as SmallTree is, is a choice about what a configuration checks, not a speed fix, and is left
  to the owner.
