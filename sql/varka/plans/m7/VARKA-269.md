# VARKA-269: Every small tree

## 1. Where this came from

Row 269 of `m7/PLAN.md`, from the plan review (2.2), item 58 and `m7/READING.md` 11. The IR fuzzer
(`VarkaIrFuzzSuite`) draws random trees from `VarkaIrGrammar`, and random draws miss corners. Item
58 called the validity and guard word algebra the one finite piece of the emitter a model could
cover; enumerating every small tree covers it without a model. The reading (SmallCheck, Korat)
gave the method: series generated by type, a size bound on node count rather than depth, and a
check of the generator against the predicate it claims to satisfy.

## 2. The admission check, done

Measured on 11 October 2026 at `bc8c96fc871`, on the laptop, one JVM, with a spike enumerator
that is the design of 3.1.

**The size.** A tree's size is the number of grammar productions in it: a leaf is one, and each
arm of `VarkaIrGrammar.Shapes` is one, however many IR nodes it builds. `make_date` over a date's
fields is one arm though its IR repeats the date three times; `weekofyear` is one arm over
`ThursdayOf`. `IsNotNull` over a column is the condition leaf, one production, as a column is the
value leaf; counted as two, no `IfElse` exists below size 5.

**The environment**, fixed so a size always gives the same series: two day columns and one
literal slot are the leaves; the month-count column only as `add_months`' count and the
trunc-level column only as `TruncDateDynamic`'s level; four inputs. Where the grammar draws
`literal()` - a literal slot, or a column when the iteration has no literal - the series takes
both, the union over the grammar's environments.

**The counts**, int lane:

| size | value trees | condition trees |
|---:|---:|---:|
| 1 | 3 | 4 |
| 2 | 90 | 10 |
| 3 | 2,829 | 267 |
| 4 | 89,434 | 8,785 |
| 5 | 2,844,764 | 317,495 |

About three to four times `READING.md` 11's estimate (1,100, 27,000, 700,000), from the second
day column and the constants each arm enumerates (seven divisors, three trunc levels, three
overflow modes, five comparisons, two range layouts).

**The cost and the first answer.** Every tree up to size 4 (101,158 under the first size rule)
was emitted under the defaults and compared with `VarkaReferenceEvaluator` through
`VarkaKernelCheck.runAndCompare`, which also runs the body the batch did not take: no failure.
One batch per tree costs 0.61 ms a tree; the four batches of 3.2 cost 2.4 ms a tree, 247 s for
size 4.

**The other direction.** The series has the grammar's magnitude gates (a calendar node over a
subtree inside the narrowed range, a checked mode where the bounds rule overflow out). Dropping
them gives an ungated series; up to size 4 (under the first size rule) it has 152 trees the
series omits. None is refused by
the emitter. 35 carry a guard `Analysis` places (`VarkaLoopEmitter.refusalsForTest`): 18
`MAKE_DATE`, 9 `DAY_RANGE`, 8 `INT_OVERFLOW`, so a batch may decline and the reference evaluator
has no spelling for it. 117 have no guard: a calendar node over a product of two columns, which
leaves the narrowed range with nothing at the IR level to report it. The compiler never builds
those (it bounds what a calendar node reads, or inserts `GuardedDay`); they are outside the
emitter's contract, and only the gate keeps them out.

**Reach.** Over the series to size 5, 979 of the 1,010 (parent, child position, child type)
triples that 20,000 of the grammar's draws contain; the 31 left nest `IfElse` under or over a
binary node, which takes six productions or more.

What the check would have rejected: size 5 in a pull request's CI (3.16 million trees), and a
size rule under which a pull request never sees `IfElse`.

## 3. The design

### 3.1 The series

`VarkaIrSeries`, test-side, beside `VarkaIrGrammar`: `IntSeries` enumerates every value tree and
every condition tree of exactly `n` productions, memoized by size, mirroring the grammar arm by
arm with its own `boundsOf` for the gates, so a tree in the series is one the grammar could draw.
`LongSeries` does the same for `LongShapes`' eight arms and `NarrowLane` at a root. The top size
streams rather than materializes, which is what lets size 6 run at all.

### 3.2 What a tree is checked against

Each tree is a projection of one value root or a selection of one condition root, emitted under
`VarkaMatrix.base` - so row 248's configurations are the option matrix's, nothing swept inside
the suite - and run through `VarkaKernelCheck.runAndCompare` (or its long twin) with the status
asserted zero. The batches, drawn once from a fixed seed inside each column's bounds:

1. length 17, every fifth row null in every column;
2. length 64, no null (the check adds its forced-masked twin);
3. length 33, a different pattern per column: alternating, every fifth, none, all;
4. length 7, every row null.

A tree up to size 3 meets all four; a larger one meets one, chosen by its index, so every batch
meets a quarter of the trees, and each batch meets both bodies.

### 3.3 Shared outputs

For every value tree up to size 3, the tree and its first value child as two outputs of one
kernel (2,919 shapes at the int lane): the child is computed once and read twice, which is what
sharing and the slot planner act on.

### 3.4 The other direction

The ungated series to the suite's size, with each tree the series omits sorted into the emitter's
refusal, a guard `Analysis` places, or outside the contract; the test asserts the three counts sum
to the omitted trees and that none is a refusal, and logs the third category's trees. A refusal
there would be a tree the grammar's gates hide that the emitter cannot hold.

### 3.5 Reach per position

The suite counts, for each size, the (parent, child position, child type) triples it reaches, and
asserts that it reaches every IR node type the grammar does by the pull request's size. The
counts are logged; a report per size lists the triples first reached there.

### 3.6 The tiers

| where | sizes | batches | trees | one JVM on the laptop |
|---|---|---|---:|---:|
| pull request (the gate, both widths) | to 4 | 3.2's rotation | 101,422 | about 75 s |
| nightly (`varka-fuzz.yml`, one JVM per core) | 5 | rotation | 3.16 million | about 40 CPU-minutes |
| an idle window (`dev/varka_series.sh`) | 5, then 6 | all four; rotation | 3.16 million; about 100 million | about 2 and 20 CPU-hours |

Sizes past 4 run through `-Dvarka.series.size` and `-Dvarka.series.slice=k/n`, a JVM taking every
`n`-th tree from the `k`-th: the emitter is not shown safe to call from several threads (row
307), so the split is across JVMs, as the nightly fuzzer's is.

### 3.7 Failures

Every failure goes through `VarkaKnownFailures.isKnown` first, as the fuzzer's does, so a known
failure does not fail this suite too. The suite runs the whole series and fails with the first
twenty failures, each with its tree, its batch and its options; the series is ordered by size, so
the first failure is a smallest one.

### 3.8 What is deliberately unchanged

The grammar, the fuzzer, the reference evaluator and the emitter. Declines as specified behaviour
are row 279's; a verdict per tree that the third category of 3.4 would need is that row's.

### 3.9 Registered op counts

None: no emitter change.

## 5. Tests, and what each is for

* **The series to size 4, int and long**: every tree against the reference evaluator, both
  bodies; the failure no random draw has met.
* **Shared outputs**: a slot or sharing bug that one output alone does not show.
* **The other direction**: a gate that hides a tree the emitter cannot hold.
* **Reach**: a series that silently stopped reaching a node type.
* **A planted bug** (`misdescribeWordLiveness`, the fuzzer's planted option): the suite fails
  under it, with a tree in the message, so the series is shown to catch what it is for.

## 7. Risks

1. **The gate's time.** 3.6's rotation keeps it near a minute; if the gate shows more, size 4
   moves to the rotation's single batch for every tree, and this plan gets a correction.
2. **Memory at size 5.** Materializing size 4 under size 5's stream holds about a hundred
   thousand trees; size 6 streams size 5's 3.16 million, which the nightly does not run.
3. **A failure the matrix finds.** The matrix runs the suite under every configuration; a failure
   there is a finding, a row, not a skip.

## 9. Outcome

Done on 11 October 2026, in one commit after the plan.

**The series to size 4**, the pull request's tier, under the defaults: 101,422 int trees and
25,816 long trees, every one emitted and compared with the reference evaluator on its batches and
both bodies, and 2,919 trees beside their first value child as two outputs; nothing failed, and
nothing was past the class-file cap. The suite's child JVM took 1 minute 46 seconds.

**To size 5**, through `dev/varka_series.sh 5 --jvms 12` on the laptop: 3,263,681 int trees and
501,396 long trees, every slice passed, in 688 seconds of wall time with the build.

**The other direction**, to size 4: the ungated series has 152 trees the series leaves out, none
refused by the emitter, 35 guarded (18 `MAKE_DATE`, 9 `DAY_RANGE`, 8 `INT_OVERFLOW`), 117 outside
the contract, each a calendar node over a product of two columns.

**Reach**: to size 4 the int series reaches 787 (parent, position, child) triples of the 1,010 in
20,000 of the grammar's draws, the long series 90 of 156; every node type the grammar draws, at
both lanes.

**Predictions scored.**

1. **Held.** No failure to size 4 at either width (the gate's wide and narrow runs), nor to size
   5 at the wide one.
2. **Wrong.** Alone on the laptop the pull request's tier took 1 minute 46 seconds in its own
   JVM, but in the gate, beside the other suites' JVMs, it took 395 seconds at the wide width and
   418 at the narrow (its JUnit times), and the gate's wide and narrow steps 853 and 863 seconds,
   against 601 and 612 on row 304's branch the same afternoon. Risk 1's remedy, one batch for
   every size-4 tree, is already the rotation; the cheaper tier is size 3 in the gate with size 4
   nightly, which is the owner's call.
3. **Held.** The planted liveness bug fails the series by size 3, with the tree in the message.

**Corrections to this plan, which is a record and is not rewritten:**

* 3.6's nightly and idle costs were the size-4 rate times the count, and a larger tree costs more
  to emit: size 5 over 12 JVMs took 688 seconds, about 2.3 CPU-hours where 3.6 says 40
  CPU-minutes. The nightly job's 150 minutes and its slices' caps of 140 hold that on a
  four-core runner at the laptop's rate; the first nightly run says whether a runner keeps it.
* 3.6 names `dev/varka_series.sh` for the idle window; `dev/varka_nightly.sh` runs it at size 5 as
  a step, with `--series-size 6` for the larger window. Size 6 has not been run.
* 3.4 says the test logs the third category's trees; it logs the first five and the count.

**The tier moved (11 October 2026).** At the owner's choice the pull request's tier is size 3, not 4
(3.6): the gate ran the size-4 series in 395 seconds at the wide width and 418 at the narrow (the
JUnit times above; 1 minute 46 seconds is the suite alone in its own JVM), and the nightly job's
size 5 already holds every tree to size 4. Size 3 keeps what the gate needs from the suite: every
tree meets all four batches, the planted liveness bug fails by size 3, and the reach test still
enumerates to size 4, being generation only. `dev/varka_series.sh 4` runs the old tier by hand. The
cost is `IfElse`, which first appears at size 4: the gate's series emits no `IfElse` tree now, and
in the gate only `VarkaIrFuzzSuite`'s random draws reach it.

A review of that change found three places where size 4 then ran nowhere, against the claim that
nothing was lost: the magnitude-gate test (`upTo = min(size, 4)`, which the nightly jobs filter
out), the narrow width (the nightly series runs at the runner's width only), and the option
matrix's configurations (the weekly matrix runs the suite at its default size). The magnitude-gate
test now runs to size 4 at any size, being generation and analysis only; the nightly job gains a
size-4 step at the 128-bit width; and the weekly option matrix passes `-Dvarka.series.size=4`.
What stays: a size-4 regression is found at night, not before a merge, and the rotation of batches
past size 3 runs only at night.

**Found 14 October 2026 by the first run of the option matrix on master** (`varka-master.yml`,
VARKA-255): under `validityByBitmap=false`, the configuration the commit's hash drew, the planted
liveness test failed with "the planted bug failed no tree to size 3", in the matrix's JVM and
again in its own. The cause is the test's premise, not the series: `misdescribeWordLiveness`
inverts the word-liveness verdict, and `Slots.plan` asks for a verdict only in a masked loop or
epilogue body under the bitmap validity pass, so with the pass off no verdict is computed and the
inversion never runs - the option's Javadoc says so, and `VarkaEmitterValiditySuite` pins it on
`year(d)`, which under the injector throws "stored but never loaded" with the pass on and emits a
class with it off. Planted over `VarkaMatrix.base`, the bug was inert under that configuration
and under `denseValidityOnce=false,validityByBitmap=false,validityOrFirst=false`, every tree
passed, and the test measured nothing. It had failed so since it landed: #719's CI ran one configuration, as
a pull request's does, no weekly matrix ran between the merge and the master run, and the test
fails the same way at the merge base before the day's merges (0f148eb7038) and at #719's own
commit. The test now plants the bug over `VarkaMatrix.base.withValidityByBitmap(true)`, as
`VarkaGuardEdgeSuite` sets the guards it tests over the matrix's options and
`VarkaReproductionEndToEndSuite` plants this bug; it passes under the defaults and both
configurations. `VarkaVariantSuite`'s planted test (VARKA-278) had the same premise, which #737
had read as the injector reaching a different set of words and listed in the skip list under both
configurations; it is planted the same way and the two lines are removed. The review of the
change asked that each failure the two tests count be the invariant's own refusal rather than
any failure, since `failures.count > 0` would take a regression, or the forced pass beside a
configuration's other options, for the planted bug - done, through
`VarkaKernelChecks.isWordLivenessRefusal` - and proposed making the injector loud without the
pass, by asking for the verdict under it too or refusing the combination in the options
builder; that is left, since either changes the emitter or the behaviour
`VarkaEmitterValiditySuite` pins for a test-only gain, and a third planting is the moment to
reconsider. The lesson is in `skills/testing-and-debugging.md`.
