  Spark's codegen order begins 1, 2, 4, 5, 0, 3, 6, ...: after the NULL-able c1 the flag is on

  The rule saw isnotnull(l) before c10 on Spark and not on Varka, no fused conjunct dropping
  null l rows, and looked for a fused puller with pulls(), which asks whether the conjunct reads

Which side was wrong
  Spark's order is ported right: codegenOrder gives Spark's placement, and the fused c6 does take
  isnotnull(l) ahead of c10. The fuzzer is right too: the reason it rejects is a fallback whose
  comment calls it unreachable while the port follows Spark. The defect is the puller search,
  which knew the two placements VARKA-380 had (a conjunct reading the column, a conjunct
  containing the tested expression) and not the third VARKA-386 ported (after a NULL conjunct, a
  conjunct that may raise takes the pending null tests written before it). The decline gave no
  wrong answer, only fewer fused conjuncts; no Spark-visible behaviour changes.

The fix
  demoteNullCheckMovers also counts as a puller the conjunct a null test is placed just before in
  Spark's codegen order (placedBefore: the first following conjunct that is not a moved null
  test). Demoted, that conjunct runs in the residual filter, which then places the null test
  ahead of it as Spark does; the rounds of behindRaising settle from there.
